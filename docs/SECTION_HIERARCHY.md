# 章节树计算与检索

`GET /file/{file_id}/outline` 与 `search_section()` 共用
`service/extraction_service.py:parse_sections()`。章节树由数据库中的 Markdown
在请求时计算，没有单独落库的树，也不需要重跑 MinerU 才能应用算法修复。

原实现主要问题：

- `1.1`、`1.1.1`、`1.1.1.1` 原本均判为同级；父节在首个子节前结束。
- 只认中文数字的“第某章”，`第1章` 被当作无编号叶子，整章检索只得到标题。
- `1.`、`(1)` 等局部条目使用固定层级，在深层数字章节中会错误关闭父节。
- `第一章` 和 `一、` 使用相同层级，中文章节与数字小节混用时缺少作用域。
- `2.5米高毛石挡土墙` 等工程图名被误判为编号；目录引导点和编号末尾点混入标题。
- 检索按标题保留最长一条，误删不同章节中的同名正文；LLM 仅选中目录时也无法找到正文。
- 前端将深度封顶为四级、无编号标题顶格，显示与实际子树不一致。

## 当前计算规则

1. 找出 Markdown 标题，保留其原文位置，拆出编号和标题。
2. 对编号识别章/节/条、中文根章、数字根章、多段数字以及局部列表。
   章/节与多段数字建立作用域；局部列表的深度相对当前作用域计算。
   中文或数字根章的后续同级章会结束前一章，即使自身没有子节。
3. Markdown 中明确保留的层级用于补充父子关系、恢复无编号标题的层级，
   不因局部出现 `##` 就覆盖全文的编号层级。
4. `end_pos` 仍是下一个任意标题的位置，`tree_end_pos` 是下一个同级或上级标题的位置。
   `content` 为自身正文，`tree_content` 包含全部子节；章节检索使用后者的边界。
5. 带尾部页码的目录候选按“编号 + 标题”对应到正文。LLM 命中目录也执行此映射。
   结果按节点去重，不再按标题删除不同编号或不同位置的正文。
6. 前端缩进按 `tree_end_pos` 中包含的祖先数计算，不对实际层级做四级截断。

## 验证与生效

- 回归覆盖多段编号、局部编号重置、中阿拉伯数字章、中文根章、混合 Markdown、
  目录映射、同名正文保留，以及 exact/contains/fuzzy/LLM 检索路径。
- 5 份样本中，相邻的数字父子节与章/节关系未再出现父切片在子标题前结束的情况。
  此检查只验证可由编号确定的关系，不代表所有 OCR 标题都已人工核对。
- 服务加载新代码后，大纲及新检索立即使用新算法。已存储的提取/分析结果不会自动更新；
  需要重新提取才会产生新结果。排查过程没有改写业务数据库或触发线上重跑。

## 信息不足时的边界

同级 `#` 中的无编号标题仍保留为叶子；缺失编号、错误 OCR、同一种编号格式被多层复用，
仅靠 Markdown 不一定能唯一恢复父子关系。目录映射要求存在可确认的同编号同标题正文，
未匹配的目录候选不会凭猜测删除。对于这类文档，应结合原 PDF/版面信息继续核对。
