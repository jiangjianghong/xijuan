# 当前队列实时对账设计

## 背景与目标

主页“当前队列”初始化时会调用 `/file/processing?type_id=...`，但后续轮询只查询前端已经跟踪的文件。本地队列为空时轮询直接返回，因此无法发现其他浏览器新上传或重新提取的任务，只有刷新页面才会重新恢复。

目标是让“当前队列”自动发现当前选中文档类型的处理中任务：浏览器窗口有焦点时最多延迟 2 秒，无焦点时最多延迟 5 秒。“查看全部”弹窗继续展示全部文档类型，不改变现有语义。

## 方案

保留现有 `/file/processing` 轻量接口，在前端每轮轮询中对当前类型进行完整对账。

每轮处理如下：

1. 读取当前选中的 `type_id`，即使本地没有真实文件任务，也查询该类型的处理中列表。
2. 将接口返回的当前类型任务合并到 `state.queue`，新增任务创建队列卡片，已有任务更新阶段和进度。
3. 对本地已跟踪但已不在处理中列表的任务，继续查询最终状态、显示完成或失败提示，然后出队并刷新文件列表。
4. 保留本地 `uploading` 和 `upload_failed` 临时卡片，不让服务端对账覆盖或删除它们。
5. 用户切换文档类型后，当前类型的响应才允许发现新任务。之前由本页启动且仍被跟踪的其他类型任务只更新已有卡片，不引入该类型的其他任务。
6. 请求返回时再次核对当前 `type_id`，避免类型切换期间旧响应把上一类型的新任务写回队列。

## 动态调度

使用递归 `setTimeout` 替换固定 `setInterval`：

- `document.hasFocus()` 为真时，下一轮间隔 2000 ms。
- 无焦点时，下一轮间隔 5000 ms。
- `window.focus` 时立即触发一次对账，随后按 2 秒调度。
- `window.blur` 时取消旧定时器，并按 5 秒重新安排下一轮。
- 同一时间最多执行一个轮询请求。焦点或类型变化不会启动重叠请求；当前请求结束后按最新焦点状态安排下一轮。

这种方式避免网络请求超过轮询间隔时产生并发响应和状态覆盖。

## 错误处理

单个文档类型的查询失败时保持现有队列状态，等待下一轮重试，不把任务误判为完成。最终状态查询失败时仍按现有行为静默处理，避免已删除文件产生无意义提示。

## 测试

前端 Node 测试覆盖：

- 本地队列为空时仍查询当前类型。
- 当前类型出现其他用户上传或重新提取的任务时自动入队。
- 不发现非当前类型的陌生任务，但继续更新本页已跟踪的跨类型任务。
- 服务端对账保留本地上传中和上传失败卡片。
- 已结束任务正常查询最终状态并出队。
- 有焦点使用 2 秒间隔，无焦点使用 5 秒间隔，焦点变化会重新调度。
- 慢请求期间不会启动第二轮并发轮询。
- 类型切换期间的旧响应不会污染新类型队列。

不修改后端接口和数据库结构。
