模型通道

文本 LLM

concurrency.global_llm

统计当前 worker 内正在执行的文本模型 HTTP 请求。默认容量 16；表名校验、文本字段抽取以及 judge/custom 分析调用共同竞争，calc 不占用。

Embedding

concurrency.global_embedding

统计当前 worker 内正在执行的向量模型请求。默认容量 4；向量写入和 vector_db 检索共同竞争。

VL 视觉

concurrency.global_vl

统计当前 worker 内正在执行的 VL 请求。默认容量 8；所有 VL 抽取方式共享，局部 max_concurrent 不能突破该总池。

业务阶段

表名校验

concurrency.global_table_validation

统计所有文件正在执行的表名判断。默认容量 10，并继续受文本 LLM 默认容量 16 约束。

字段抽取

concurrency.global_extraction

统计所有文件正在执行的字段抽取。默认容量 8，实际还可能进入文本 LLM、Embedding 或 VL 模型通道。

逻辑分析总池

concurrency.global_analysis

文件管线规则与独立分析规则共享同一个总池。以默认配置为例，两类来源合计最多同时执行 8 条规则。judge 和 custom 规则还需要文本 LLM 槽位，calc 规则不占用文本模型通道。

单文件限流（不在本页展示）

为什么看不到

concurrency.task_table_validation / task_extraction / task_file_analysis

这三项限制单个文件内部的并发，仍然真实生效，只是不在运行台展示：当每文件上限与对应全局池同量级时，它们会常年显示 100% 饱和，而全局池远未跑满，图与实情相反。被它们吸收的排队改由各池详情里的端到端等待体现——端到端明显大于本闸等待，就说明背压堵在这一层。

怎么配才有用

单文件值必须小于对应全局值才起作用。task_table_validation=4 配 global_table_validation=10 能保证至少 2 个文件并行；两者相等时单个文件就能占满全局池，这一层形同虚设，后到的文件会被前一个大文件的几百张表堵在队尾。相等或更大时启动日志会给出告警。

独立接口

独立分析

concurrency.independent_analysis

独立分析统计所有 /analysis/run 请求正在处理的 item，不限制单个请求。以默认配置为例，当前 worker 内所有独立分析请求合计最多同时处理 4 个 item。每个 item 内的规则仍按顺序执行，每条规则继续受“逻辑分析总池”默认上限 8 约束。

管线

文件管线

concurrency.global_pipeline

统计完整文件管线任务。默认配置值 4 目前尚未接入调度，只显示“未接入”，不产生控制效果。
